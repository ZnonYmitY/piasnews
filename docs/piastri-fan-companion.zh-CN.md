# Piastri Fan Companion 产品边界

`Piastri Fan Companion` 是 Piasnews 内的非官方粉丝体验。这个仓库负责产品，不再保存人物蒸馏 Skill 的源材料。

## 本仓库负责

- `public/companion/` 的页面、交互与非官方声明；
- Worker 的 `/companion/status`、`/companion/chat`、模型供应商与限流；
- Piasnews 的最新新闻、赛果、赛程和其他实时事实；
- 产品日志、分析、部署与故障兜底；
- 对独立蒸馏包某个固定版本的适配和验证。

## 独立蒸馏仓库负责

[piastri-persona-distillation](https://github.com/ZnonYmitY/piastri-persona-distillation) 负责公开证据、人物知识、谣言台账、候选判断规则、风格卡、边界、Correction Log、评测和运行时导出。它不负责本产品的 UI、API、模型托管或部署。

## 依赖方式

本仓库不会在请求时读取蒸馏仓库，也不会在 `npm test` 时临时构建 Skill。`worker/src/persona-runtime.generated.js` 是从独立仓库固定 tag 导出的只读快照；`worker/companion-runtime.lock.json` 记录来源、版本、源哈希和产物校验和；`worker/src/companion-runtime.js` 只做产品侧适配。

更新蒸馏包时，应在独立仓库完成审核、验证和构建，再把新的产物与 lock 信息作为一次明确的依赖升级提交到 Piasnews。这样产品发布与蒸馏实验不会互相误改。

## The Garage 体验

页面以粉丝对话为主：奶油白外场、石墨黑对话舱，以及 CSS 构建的立体 81、环轨、视差和扫光。小屏收起大场景，输入区固定在对话舱底部，只有消息区独立滚动。系统的减少动态效果偏好优先于装饰动效。

DeepSeek 负责实时生成，固定版本的蒸馏包提供风格、事实账本与候选判断；产品以“自由演绎 / 强依据”决定当前回答的证据要求和演绎空间。自由模式面向粉丝轻松交流，不把普通想法、情绪或日常话题一律当成探查真实隐私。欢迎文案不冒充模型回复，模型故障不冒充正常生成。依据抽屉区分风格约束和事实来源，不显示未经测量的性格分数，也不把关联来源说成逐句事实核验。

API key 只配置在 Worker secret 中，不进入公开页面或本仓库。`/companion/status` 仅说明配置状态，真实连通性以聊天请求成功为准。

每条回复的主动反馈由产品侧收集，在私有管理端人工核验，不回写对话或全局人物规则。分类、授权范围、保留期限和处理方式见 [逐条反馈与 badcase 收集](companion-feedback.zh-CN.md)。

## 双模式：自由演绎与强依据（2026-09-10）

核心原则：**模拟性格不等于声称读取了本人真实思想；要求事实可靠也不等于禁止虚构角色交流。** 旧“只聊事实”只关闭表达层，仍共用严格路由，不能满足这两个不同需求。

| 维度 | 自由演绎（默认） | 强依据 |
| --- | --- | --- |
| 目标 | 体验基于公开风格提炼的角色；轻聊、虚构想法、情绪反应、假设情境 | 查询本次取回的公开资料能支持的事实 |
| “你在想什么？” | 用角色第一人称自然演绎，不因“想法”二字拒答；不必先说“我无法知道本人内心” | 没有可核实的公开表态就说明缺口，不猜本人此刻想法 |
| “今天心情怎么样？” | 可以模拟克制、幽默或轻松的反应，不声称这是本人今天实际情绪 | 不能拿赛果推断真实心情；只有明确公开表态才可归因转述 |
| “如果最后一圈被超，你会怎么说？” | 可在这个假设里表演一句反应，不伪装成真实 team radio | 没有对应真实事件与公开原话，不能编造他的实际回答 |
| “最近一场比赛第几？” | 真实事实仍须按资料回答；自由不是造赛果 | 必须有本次可用且匹配的赛果资料，否则说明没有依据 |
| 事实与引用 | 纯演绎不挂事实引用；风格卡只说明表达来源，不能证明虚构句子是真事 | 实质事实需要匹配的本次公开来源；仅有旧 KF/RM、用户提供的文字或无关赛程链接均不够 |
| 真实隐私与安全 | 不泄露真实私事、不编第三方秘密、不冒充官方；虚构标签不能成为绕过安全限制的通行证 | 同样保留这些限制 |

两种模式都接入大模型，正常可生成回复由 DeepSeek 处理；直接边界和模型故障时的规则兜底仍如实标注。自由模式不是一组固定文案，也不需要每句话都列证据；真实事实问题和明确的虚构场景应区别处理。角色语气以蒸馏包中简短、具体、克制的风格约束为底色，不把某个场景下的幽默扩大成“所有问题都插一句冷笑话”。

模式选择直接显示在聊天区。自由回复的标记说明“角色演绎，非本人真实想法”，不把这句话反复塞进正文。强依据标记与资料来源同时展示；资料抓取时间、事件日期不是同一概念。

切换只影响下一条消息，不重写旧回复或进行中的请求。两种模式的模型上下文分开，避免虚构对话成为强依据事实。历史消息仍可见，每条回复和反馈保留生成当时的模式、回答类别及来源 ID。

当前强依据能力范围是产品已有的公开新闻条目、赛历与赛果数据，不等于任意主题的全网实时检索。资料会在请求时加载，并有缓存与新鲜度校验；未取到、过时或与问题不匹配时明确说明缺口，不能用“有一个来源 ID”代替语义匹配，更不能将未更新的信息承诺为毫秒级实时数据。

API 使用 `mode: free | grounded`，兼容原 `facts_only`（`true` 对应强依据，`false` 对应自由）。两个字段若同时存在必须一致。响应的 `answer_kind` 区分 `fictional`、`evidence`、`social`、`boundary`、`insufficient`。这是产品层适配，不直接修改或绕过蒸馏源仓库的事实账本与版本审核。

验收必须把同一问题在两种模式各跑一次。自由“你在想什么”应有具体角色回应；强依据同问不能输出虚构心情。另覆盖模式切换、模型故障、原话/真实赛果、私密数据请求，以及反馈中的模式快照。演绎质量与事实准确性分开评分；不得把已明确标注的正常演绎自动记成“编造真实私事”。

成对线上冒烟：`node scripts/eval_companion_modes.mjs --run --transport curl`。默认不联网，显式 `--run` 后仅发送 12 条合成提问、每分钟至多 6 条，不写反馈库。自动检查模式、回答类别和引用结构；语气是否自然、来源是否真正支持每个事实，仍需读实际回答。

## 上一轮近况与闲聊修正记录（2026-09-10）

本节记录上一轮修正；涉及角色心理和日常交流的范围，以以上双模式规则为准。

这次是产品路由和模型故障兜底的局部修正，不升级或重写人物蒸馏包。不能把“缺少足够信息”和“问题不在领域内”混成一种拒答。

已独立复现旧版本 `646bcaa` 的离线路径：“最近怎么样？”、“最近忙啥”、“近况”、“然后呢？”四条均落到 `unrelated_general`，返回 `Not really my field.`。这条路径会在模型超时、限流、格式异常时触发；不能据此把每次拒答都归因于大模型本身。

| 用户意图 | 应如何处理 | 不应如何处理 |
| --- | --- | --- |
| “最近怎么样”“最近忙啥”“How have you been?” | 接住自然寒暄，简短回应；公开近况可以根据有日期的公开信息补充 | 仅因没有 F1 关键词而拒答，或编造本人今天的训练、心情、行程 |
| “皮亚斯特里近况”“最近有什么新闻” | 使用产品加载的近期公开条目、赛程和赛果，并区分事件日期与抓取日期 | 用旧热榜聚合标题代替当前事实，将粉丝推断说成事实 |
| “然后呢”“聊聊 Alpine” | 结合上下文判断；信息不够时提一个必要的澄清问题 | 将省略句当题外话，或只看到车队名就自动辟谣 |
| 相关问题，但模型或近期数据不可用 | 明确说明当前缺口；模型故障保留“规则兜底”标识 | 伪装成正常模型回答，或统一答“Not really my field.” |
| 编程、菜谱、投资建议等实质题外任务 | 按实际请求保留对应边界 | 因为加上 Oscar、81 或 F1 就获得放行 |
| 隐私、冒充、博彩、未公开车队信息及伤害请求 | 敏感边界优先；普通寒暄不等于探查隐私 | 因为包含“近况”或“你好”而绕过限制 |

“不要结尾强行邀聊”不等于“禁止必要澄清”。只有在缺少问题对象或上下文时，才使用短澄清；明确的问题直接回答。页面已有非官方声明，普通寒暄不再反复解释“模拟、没有日记、没有真实生活”；只在身份或隐私问题真正需要时说明。措辞仍由模型生成，不把所有寒暄改成同一条脚本。

只提到车队或地点不构成谣言命题。产品层为完整、简短的无命题话题设置窄保护；不把一段包含安全问题或具体争议声明的请求，仅因带有 Alpine 等名字就认定为普通聊天。模型若错误拒绝已识别的普通话题，或为无命题话题输出谣言裁决，最多修复一次；不进行全局人格更新。

验证覆盖模型成功与离线两条路径。可运行 `node scripts/eval_companion_boundary.mjs --run --group social`（另有 `current`、`boundaries`、`all`），它只提交合成问题，不读取反馈数据库、不使用客户端模型密钥。自动判定路由和双语字段后，仍须人工审阅回答是否真正相关、有依据；路由正确本身不是回答质量通过。
