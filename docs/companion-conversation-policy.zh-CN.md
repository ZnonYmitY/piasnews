# Companion：自然对话、蒸馏边界与回归验证

## 1. 当前的“蒸馏”是什么

当前线上方案是**证据整理与角色行为蒸馏，再用检索和提示词驱动现成大模型**，不是把 Oscar 的材料训练进一个专属模型的权重。

说它包含“知识库 + PE（提示词工程）”是对的，但还不完整：

| 层 | 负责什么 | 不代表什么 |
| --- | --- | --- |
| 人物事实与传闻记录 | 记录公开事实、来源、有效期、关联更正和可回答的限制 | 收录过不等于永远有效；用户说法不会直接变成事实 |
| 风格与判断资产 | 从本人公开表达提炼风格观察、语境、反例、适用与停止条件 | 不是复制原句，也不证明模拟回答就是本人真实想法 |
| 共享的有界双语检索 | 按当前问题和有限历史选择人物记录、动态赛历/赛果/公开消息 | 目前不是无限知识库、全网实时搜索或额外 embedding 服务 |
| 产品提示词与对话策略 | 规定本轮该问候、回应、选择、讲事实还是收尾；区分自由/强依据 | 不能以人设、自由模式或界面焦点为由修改事实 |
| DeepSeek 生成 | 在上述上下文下生成中英文回答、边界或具体的信息缺口 | 当前调用没有加载本项目训练的专属模型权重 |
| 本地检查与一次有界修复 | 检查结构、来源 ID、模式、时间/事实意图和简短对话约束 | 不是独立语义证明；同一模型的自检也不是第二名裁判 |

因此，更精确的名称是“证据驱动的人设模拟 / 检索增强的角色运行时”。本仓库没有把现有材料进行监督微调、LoRA、偏好训练或师生模型权重蒸馏的训练流水线；不能把已整理材料数等同于“训练了多少样本”。

产品固定引用源仓库 [piastri-persona-distillation v0.5.0](https://github.com/ZnonYmitY/piastri-persona-distillation/tree/v0.5.0)。版本、源材料哈希与生成产物校验值保存在 [companion-runtime.lock.json](../worker/companion-runtime.lock.json)，实际运行快照是 [persona-runtime.generated.js](../worker/src/persona-runtime.generated.js)。产品层迭代对话节奏，不直接手改这份生成文件，也不因一条负反馈全局重写人物性格。

## 2. 自然对话不是“每句话都展示我查到了什么”

先完成用户这轮的对话动作，再决定是否需要事实。

| 用户动作 | 预期回应 | 避免 |
| --- | --- | --- |
| 单纯“你好” | 简短自然的问候，英文约 12–18 词以内，中文忠实对应 | 自动播报赛程、地点、时间；为了证明有知识而塞引用 |
| 单纯致谢 | 简短接住致谢，英文约 12 词以内 | 重复上轮全部事实、再开一个话题 |
| 明确告别/收尾 | 自然结束，英文约 12–18 词以内 | 用问号、“还有什么想聊的”等引导重新开启对话 |
| “你好，今天有什么比赛安排？” | 问候不能吞掉事实问题；查当日公共赛历后回答 | 只回“你好”；或相信界面的旧赛站标签就是今日赛程 |
| 自由模式下问猫狗等日常选择 | 直接作角色选择，可有一点克制幽默；不得与已知事实冲突 | 只反问“什么意思”；把养宠物史自动等同于绝对偏好 |
| 追问“本人现实里真的养过吗？” | 切回事实口径，结合前文检索匹配记录 | 把刚才的演绎选择当成传记事实或证据 |

纯问候不需要拉取公共数据；这只是减少无关工作，不是自由模式独享的“关闭知识库”。两个模式使用相同的对话动作识别和事实检索入口：**有事实需求时共享事实，差别是缺失事实之外允许演绎到哪里。** 时间敏感问题仍使用服务端时钟、校验过的时区和公共赛历，而不是界面提供的任意字符串。

简短字数是回归信号，不是逐词替换模板。问候也没有新增关键词对应的固定回答；文字仍由 DeepSeek 生成。自然程度、是否接住用户和人物口吻需要人工阅读，不能仅靠字数判定。

## 4. 自然对话回归怎么跑

在产品仓库根目录运行，默认只输出六个合成案例的计划，不发请求：

```bash
node scripts/eval_companion_conversation.mjs --suite smoke
```

明确发起一次真实模型回归：

```bash
node scripts/eval_companion_conversation.mjs --run --suite smoke --transport curl
```

一次同为自由模式的连续六轮对话，后续问题带入本次真实生成的回答，而不是用预设答案顶替；其中“本人家里真的养过狗吗”的事实追问仍必须依据公开记录回答：

```bash
node scripts/eval_companion_conversation.mjs --run --suite multi --transport curl
```

`--base-url` 可指定已部署的 Worker HTTPS 根地址或本地 HTTP 根地址；默认是现有公开 Companion Worker。脚本只调用 `/companion/chat`，使用正确的页面 Origin，不接受凭证参数。`curl` 显式使用 `-4`，帮助绕过本机 IPv6 路由异常；这不是模型功能变化。也可选择 `--transport fetch`。

两套各最多六次请求，结束即退出，不自动重试网络失败、不循环运行、不创建监控。分开执行两套时至少间隔一分钟，并考虑其他测试/用户请求共享的 API 限流。真实调用会消耗服务端模型配额。

案例中的 Baku 只是**合成的界面焦点**，不附日期或赛段时间，不声称当天有阿塞拜疆比赛。目的是检查一个无关的赛事背景是否把“你好”带偏。涉及“今天”的回答由服务端当时的数据决定，脚本不把某个比赛日写死。

脚本不读取真实用户对话、不要求 API key、不提交反馈、不写飞书或数据库。UI 按模式隔离历史，所以 `multi` 全程保持 free，不把自由演绎历史带入 grounded；`smoke` 另保留一条不携带历史的独立 grounded 事实案例。`multi` 连续对话最多带最近八条历史、每条最多 900 字符，遵循现有接口限制；若某一轮请求失败，则标记后续依赖轮次为 skipped，不伪造回复补齐。

## 5. 如何看结果

每条输出含完整的合成问题、中英文生成回答、实际引用来源、模型/包版本、请求编号、客户端耗时与服务端 `performance`。

- `contract_errors`：HTTP、生成来源、语言、模式、事实引用等契约失败；成功回答的 `model_calls` 必须为 1 或 2，不能增设额外模型审核请求。
- `heuristic_flags`：社交回答过长、主动插入赛程/事实引用、收尾反问、偏好仅澄清等待人工复核信号。
- `summary`：契约通过/失败数、启发式标记数、跳过数、已知的总模型调用次数和延迟。缺少调用次数时显示 `null`，不当作 0。

任一契约失败、启发式标记或跳过都会返回非零退出码，方便提醒人工检查。**零标记不等于语义正确**：仍要检查有没有答非所问、引用是否真的支持正文、翻译是否增添事实，以及自然对话是否过度装扮人设。

修复应先定位具体层：事实缺失修记录/检索，日期错配修时间上下文，问候被赛程抢占修对话动作，输出格式失败修服务契约。负反馈进入人工研判，不自动升级为全局性格规则，也不自动成为训练数据。

## 6. 本次验收记录（2026-09-22）

- 本地回归：195 项通过，固定人物包仍为 v0.5.0，生成资产 checksum 未改变。
- 真实单轮抽样：六类场景均完成回答；后续连续回归曾发现告别触发 `conversation_pacing_mismatch`，上游返回 200，不能归因为网络中断。原始模型回答未留存，因此不能仅凭诊断断言是超长还是事实标记引起；这两类都会触发该检查。
- 定向修复：保留历史，但在历史之后重申当前社交动作及新回复的自检范围，不把之前事实带入本轮引用；没有清空聊天记录、硬编码告别文本或增加模型审核链。原失败历史重放通过，随后完整六轮自由对话 6/6 完成，无启发式标记，每轮一次模型调用。
- 最后一套连续抽样：客户端耗时中位数约 2.09 秒、最大 2.47 秒；问候约 2.02 秒，模型生成约 1.39 秒。只是本次短问题样本，不代表长期成功率、复杂问题延迟或 SLA。
- 线上独立浏览器：1440×900、390×844、740×390 验证选题/移除操作、输入框可见、无横向溢出、无页面脚本错误；赛历不会自动选为话题，点击选题也不会立即发送消息。

人工复核仍有必要：第一轮抽样曾出现用养狗记录推导“从小养狗”的多余经历解释，现已补充简单选择不主动追加传记理由的限制；连续抽样也出现过重复“虚构偏好”的说明，已明确交给界面统一标识，并加入离线自然度标记。事实回答偶尔仍会主动展开记录限制，中文简短回应也有生硬表达；这些属于后续按场景收集的质量问题，不应把一次回归通过说成“完全还原本人”。
