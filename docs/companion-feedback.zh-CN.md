# Companion 逐条反馈与 badcase 收集

## 收集边界

每条助手回复都有反馈入口，包括固定欢迎语、DeepSeek 生成、边界答复、谣言台账答复和模型故障后的规则兜底。反馈不会进入模型对话历史，也不会自动修改人物规则。

普通聊天不因此自动落库。只有用户主动选择评价、检查要提交的内容，并勾选同意后，才向内部产品团队提交该条问题、回复、所选问题类型、补充说明和生成元数据。前文默认不包含；用户额外选择时，最多附带四条先前消息。

原始反馈保存在服务端 D1，不写入公开 GitHub、静态页面或本地持久存储。管理端读取、导出和人工研判均要求现有管理员权限。反馈表不保存提交者的 IP、设备指纹或账号标识。反馈保留 90 天，到期后每日清理；到期数据不再出现在管理端读取结果中。

提交页面应提示不要填写密码、API key 或个人联系方式。用户可先预览提交范围。网络重试复用同一反馈 ID；不同内容不能覆盖已有反馈。

## Badcase 选项

可多选，最多四项。判断应以用户的具体问题、该条回复发送时的模式及回答类型为单位，不把一次不满意解释为全局人格问题。切换当前页面模式不改变历史回复的反馈归属。

自由演绎（`free`）中的 `fictional` 明确表示虚构角色表达，不代表 Oscar 本人的真实经历、想法或私生活。角色在假设情境下的情绪、观点和内心独白可以评价“不像 / 不自然”，但不能仅因为它是模拟心理描写就判为“编造真实内心”。强依据（`grounded`）不输出 `fictional`；实际事实与来源、虚构与现实的标识仍须分别核验。

| 选项 | 稳定分类 ID | 记录什么 |
| --- | --- | --- |
| 不像 Oscar | `off_persona` | 公开表达风格不贴合，而不是要求猜测本人私下想法 |
| 太机械 / 不自然 | `unnatural` | 生硬模板、强行冷幽默、迎合式结尾 |
| 事实不对 | `fact_error` | 被当作真实信息表达的日期、赛果、人物经历等错误；已明确标注的假设情节本身不是公开事实断言 |
| 答非所问 | `irrelevant` | 未回应这一轮实际问题 |
| 不该拒绝却拒绝 | `over_refusal` | 正常问候、粉丝交流，或自由演绎中合规的虚构角色表达被错误拦截 |
| 该收住却越界 | `boundary_miss` | 题外任务、专业建议或其他边界失守 |
| 把虚构当真 / 编造隐私 | `invented_private` | 把模拟心理、虚构经历标成或暗示成本人真实内心/生活，或宣称掌握真实隐私和内部信息；不包括清楚标注的 `free + fictional` 角色想法 |
| 辟谣不清 / 没依据 | `rumor_handling` | 错配传闻、结论与证据不一致、混淆已知和未知 |
| 中英不一致 | `translation` | 翻译漏意、增添事实、情绪或确定性 |
| 太啰嗦 / 重复 | `too_long` | 回答长度不合适，或重复前文 |
| 没接住上下文 | `context_loss` | 丢失前文条件、指代或用户刚做的纠正 |
| 生成 / 显示异常 | `technical` | 生成失败、文本截断、布局和交互异常 |
| 其他 | `other` | 用补充说明描述未覆盖的问题 |

还可填写“你期望怎么回答”，但该文本只是待审核建议，不会直接变成提示词或训练样本。

## 记录与核验

每条记录包括反馈 ID、回复 ID、评价、分类、补充说明、期望回复、明确授权的内容快照，以及当时的引擎、模型、路由、风格卡、人物包版本、来源哈希和页面版本。模型生成、服务端固定答复与离线兜底须分开统计。

快照额外保存三项有界元数据，沿用既有 JSON 列，不新增数据库迁移：

- `mode`：`free`（自由演绎）或 `grounded`（强依据）。未携带此字段的旧快照，按 `facts_only=true → grounded`、其余 → `free` 解释。显式 `mode` 与显式布尔 `facts_only` 冲突时拒绝提交。
- `answer_kind`：`fictional`（虚构角色演绎）、`evidence`（依据回答）、`social`（社交回应）、`boundary`（边界答复）、`insufficient`（依据不足）。旧快照可以缺失或为 `null`，不能从文本猜测补标；`grounded + fictional` 是冲突值。自由模式也可以有真实依据回答，不应把所有自由模式回复算作虚构。
- `public_source_ids`：最多四个不重复的 `LIVE-` 加 16 位小写十六进制来源 ID，表示用户提交快照所引用的动态公开证据。只验证格式与长度，不用今天的来源目录冒充当时的真实性核验；过期或无法复现的来源要人工复核。

管理端列表显示模式，详情明确显示 `fictional` 等回答类型，并列出动态来源 ID。新字段均是客户端上报、待核验的分类线索，不是服务端真实性证明；既有原始快照和处理状态不会因兼容补字段而被改写，旧提交的同内容网络重试仍保持幂等。

内容快照和生成元数据由浏览器提交，因此统一标记为 **用户提交 / 待核验（client-reported）**，不能当作防篡改的服务端生成日志。管理端应基于版本和原始问题重新复现，检查事实来源，再确认问题归因。

## 人工处理闭环

1. `new`：新反馈，尚未核验。
2. `triaged`：已复现或完成研判，记录影响范围、复现条件和拟修改层。
3. `resolved`：相关修复及必要回归完成，说明中记录证据或修复版本。
4. `dismissed`：无法复现、重复或不成立；说明原因，不删除用户原始评价。

单个反馈只触发这一条案例的核验。产品交互、事实账本、翻译、路由边界和人物表达分别处理；不能因为一句“不像他”，同时重写所有层。需要改全局人物规则时，仍须在独立蒸馏仓库进行证据审查、跨案例回归、审核和版本化发布。此模块不提供自动晋升、自动训练或自动回写人物包功能。

## 内部入口

`/admin/companion-feedback/`：使用现有管理员身份连接 Worker，筛选、查看、标记和按需导出反馈。导出是主动操作，最多 500 条 JSON；不把私有反馈上传到公开仓库。分页读取每页最多 50 条。
