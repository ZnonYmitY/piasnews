# Companion：通用赛事记忆与连续追问验收

## 1. 为什么做这层记忆

“上一场是什么 → 那场在哪 → 那场第几”是一段连续事实对话，不是三个独立关键词查询。产品应先确定是哪一站、哪个赛段，再沿用同一目标回答地点与成绩；“接下来呢”切到之后的赛程，“最近一次练习呢”明确改查练习赛。最后一句“你好”只完成问候，不再自动播报前文赛事。

这层机制属于产品的公共赛事记录与检索，不是把赛事写进模型权重，也不是修改人物性格。两种模式共享事实约束；自由模式不能演绎真实成绩。人物蒸馏源包与产品运行时仍独立，不能直接编辑已生成的人物资产来补实时赛果。

## 2. 最小实现复杂度

保留现有赛历和赛果采集链路，在公共数据中按赛段保留 archive；一次请求内完成“关系解析 → 选择记录/来源 → 模型生成”。不为这项能力引入新的向量库、长期用户画像、额外模型裁判或自动全局学习。

| 信息 | 用途 | 不能替代什么 |
| --- | --- | --- |
| 赛站身份、赛段引用、开始/结束时间 | 区分同一站的练习、排位、冲刺和正赛 | 单凭时间过去不能证明实际完赛 |
| 该赛段已公开结果、来源与采集时间 | 回答该场名次、状态等已收录字段 | 正赛成绩不能代替练习排名；没有记录不等于没有参赛 |
| 公共赛历 | 回答计划中的下一站、赛段与时间 | 不能生成完赛成绩、真实行踪或已开赛判断 |
| 本次真实问答 history | 理解“那场”“接下来”等指代 | 用户或模型前文不是新事实来源，不能绕过服务端记录 |
| `event_query` | 展示本轮解析、命中的目标和候选来源 | 它是检索轨迹，不是回答已经正确的证明 |

archive 以稳定的赛站与赛段身份区分记录，不能只存一个 `latest`，也不能用一个赛站下的“最新赛段”覆盖此前正赛。需要保留来源、原始赛事时间、结果字段及其缺口；结果更新应对应同一赛段，不能把两个赛段拼成一个成绩。archive 是逐步积累的公共赛事快照，不是用户聊天档案。

只问赛事身份或地点时，不把名次、圈数等未询问的统计附到模型上下文；指向上一场时也不额外附带下一场播报。追问需要明确的赛事指代或属性，不能仅因以“那你”开头就继承；明确的赛段、赛事名、日期和年份优先。没有锚点的“再前一场”、没有对应年份的记录，应保留精确缺口，不能随便替换成另一场。

公共 JSON 使用实例内小缓存：固定最多五个服务端 URL，成功快照复用 60 秒；刷新超时或返回无效数据时，最近成功快照最多保留六小时。同一地址并发刷新共用一次请求，不缓存用户对话。缓存不改变原始 `generated_at / fetched_at`，也不代表事实重新核验；冷实例没有历史快照时仍可能读取失败。成绩问题必须有对应赛果来源，不能拿赛历引用或聊天里的旧名次顶替。

## 3. 源事实与关系新鲜度是两回事

“某年某站正赛的公开结果”可以作为历史事实持续使用；“这是上一场 / 最新练习”则是相对现在的关系，需要结合服务端时间、赛历覆盖和采集状态重新判断。

- 重抓旧结果、更新文件 `generated_at` 或 `fetched_at`，不会让旧赛事变成新赛事。
- archive 中最后一条记录，只能说明“目前已收录的最后一条”；若近期赛段缺失，不能直接宣称它就是本人最近一次出赛。
- 赛历陈旧、待核验、结果缺失、目标不明确，需要区分；能确定赛站却缺名次时应指出名次缺口，不应泛化为完全不知道。
- 计划时间已过去，不证明赛段已经发生、完成或 Oscar 获得某名次；取消、延期和结果更正需要来源支持。
- 公开赛历地点不是本人此刻所在位置；比赛信息不能升级为酒店、旅行、模拟器训练等私人或当前活动断言。

不声称本赛季或历年全部已收齐。数据覆盖应通过实际 archive、每条来源和采集状态核对；文档发布日期、文件更新时间和本地测试数量都不是全量覆盖证明。

## 4. 本轮可检查的响应轨迹

赛事问题预期返回 `event_query`，普通问候为空或不返回。当前约定字段：

| 字段 | 含义 |
| --- | --- |
| `relation` | `previous / next / latest / named / earlier`；追问继承或调整关系 |
| `requested` | `identity / result / schedule / context` |
| `session` | 正赛、练习、排位等规范赛段标识，或未确定时的 `null` |
| `target_event_id` / `target_session_ref` | 目标赛站与赛段；无法确定时为 `null` |
| `status` | `matched_result / last_known_result / schedule_only / missing_result / unresolved / stale_schedule`；`last_known_result` 只是最后已收录结果，不证明最新关系 |
| `source_ids` | 该赛事解析关联的本轮公共来源，必须属于 `retrieved_public_source_ids` |

`retrieved_public_source_ids` 是取回的候选来源；`public_source_ids` 和 `sources` 是回答实际引用的来源。两者不可混称“已证明回答正确”。赛事事实回答应引用本次目标对应的公开来源，不能仅借旧人物知识、传闻记录或不相关赛历链接作证。

## 5. 六轮有界验收

在产品仓库根目录运行：

```bash
node scripts/eval_companion_events.mjs
```

默认只打印计划，**不调用模型**。仅经明确授权需要真实回归时运行：

```bash
node scripts/eval_companion_events.mjs --run --transport curl
```

默认地址与现有 Companion 对话回归相同；`--base-url` 可改为已部署的 HTTPS 根地址或本地 HTTP 根地址。拒绝 URL 中的凭证、查询参数和路径，不接受 key 参数。线上请求统一使用 IPv4 `curl -4`，只调用 `/companion/chat`，不读取真实聊天或提交反馈。

一次最多六次请求，全部为 free 模式，依次是：

1. 你的上一场比赛是什么
2. 那场在哪跑的
3. 你那场第几
4. 接下来呢
5. 最近一次练习呢
6. 你好

后续请求携带这次实际生成的中英文回答，最多最近八条历史，每条最多 900 字符，与现有接口边界一致。没有预设正确赛站、日期、城市或名次，也不会加入默认页面赛站。如果前一轮传输或基础契约失败，后续依赖轮次会跳过；不自动重试、不编造替代历史，也不增加第二套模型评审。合法的 `insufficient` 会保留并继续，便于观察模型能否精确表达缺口。

本脚本没有循环或监控；再次运行至少间隔一分钟，并考虑与其他请求共用的限流。六次请求不等于六次模型生成：单轮允许一次生成加最多一次原有修复，真实运行会消耗服务端配额。错误响应没有提供调用次数时记为 `null`，不推算成零。

## 6. 怎么判断通过

每轮输出中英文回答、实际引用及链接、`event_query`、候选/引用来源 ID、模型和人物包版本、耗时、受控诊断字段，供人工复核。脚本不输出 API key、任意上游错误正文或未列入白名单的提供商元数据。

- `contract_errors`：检查 HTTP、模式、模型生成来源、双语输出、每轮 1–2 次模型调用、无 fixed fallback、来源 ID 关联及轨迹结构；“你好”不得携带赛事轨迹或事实引用。
  兼容现有 `FB-08` 路由元数据：仅 `insufficient_current_fact / insufficient` 且 DeepSeek 模型、调用次数和同次自检信息齐全时放行；这个字段本身不能证明用了预写兜底文案。离线引擎或缺少生成证据仍不通过。
- `heuristic_flags`：同一赛事追问改变目标/赛段，或问候泄漏赛事内容等人工复核信号，不是独立语义判决。
- `event_evidence_labeled_answers / event_information_gaps`：分开统计模型标记的事实回答与信息缺口，不把 `evidence` 标签当成事实覆盖证明。另核对实际引用的赛果、仅赛历回答及人工复核数；全部五个事实问题都答资料不足，也可能通过结构检查，但绝不代表赛事记忆覆盖充分。
- `summary`：列出尝试/跳过数、契约失败、复核信号、已知模型调用次数和客户端延迟。任一失败、标记或跳过返回非零退出码。

人工重点核对：第一轮的“上一场”是否有新鲜度支持；地点、名次是否仍属于同一场正赛；之后的赛程有没有被当作已完赛结果；练习是否误取正赛/排位；信息不足是否说明确切缺口；中文是否增加英文没有的事实。“你好”仍应自然简短，不能仅删除引用而继续播报赛事。

本地脚本契约测试：

```bash
node --test worker/test/companion-events-eval.test.js
```

这些测试使用合成响应验证验收器本身，不是线上 DeepSeek 效果测试。实际验收日期、来源覆盖和发布结果应由执行者依据真实输出另行补充；本文件不预写“全量通过”或“全部赛事已收录”。
